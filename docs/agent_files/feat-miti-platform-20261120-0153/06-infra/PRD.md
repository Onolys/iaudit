# PRD: SP06 infra — GCP resources, hosting/domains, CI/CD, config

Repo/branch: Onolys/onolys (local `iaudit`) / `feat/miti-platform` · Depends on: none (Phase 1); satisfies SP04 "SP06 interface", SP05 manual steps, SP07 admin host needs · Owns: `infra/**` (Terraform + scripts), `.github/workflows/{deploy-staging,deploy-prod,_deploy-cloudrun}.yml` (`_deploy-cloudrun.yml` is a reusable `workflow_call`, also used by SP07's `deploy-admin.yml`), that `config/{staging,prod}/stt_providers.yaml` and `routes.yaml` exist and are copied into the image (their format and contents are SP01's), root `.firebaserc`, root `firebase.json` + `firestore.rules` (Firestore only; web hosting config is SP05's `web/firebase.json`), `docs/reference/infra.md` (runbook, env var table, DNS list), `docs/decisions/0022-infra-*`

## TL;DR
One GCP project (`onolys`), one region (`us-central1`), two environments (`staging`, `prod`) provisioned by Terraform (state in a GCS bucket; no gcloud needed, runs on this machine with ADC). CI (GitHub Actions, Workload Identity Federation, no JSON keys) builds one image, deploys staging on merge to `main`, prod on a gated manual run that promotes the same image digest. `app.onolys.com` = Firebase Hosting site with `/v1/**` rewritten to Cloud Run `api` (resolves SP04 [OPEN]). Tejit's tasks: DNS records, budget amount, Google sign-in toggle, email templates, billing/Owner access, Anthropic API key, admin email allowlist.

## Problem
Nothing exists for the platform: SP04/05/07 each list resources they need, but nobody owns creating them, wiring IAM, deploying, or the DNS records. Landing already uses project `onolys` (Hosting sites `onolys`, `onolys-redirect`) [verified: `firebase hosting:sites:list --project onolys`], so new things must not disturb it. This machine has `firebase` CLI logged in, user ADC with quota project `juno-medical-clarity`, no `gcloud`/`terraform`/`docker` [verified: `which`]. Reference app simplify-med deploys with bash+gcloud in one workflow and a long-lived `GCP_SA_KEY` secret, and has no IaC [verified: `.github/workflows/deploy.yml`, no `infra/`]; we copy its api/worker one-image split and `SERVICE_MODE`, not its key handling.

## Goals / Non-Goals
**Goals:** all resources reproducible from code; staging and prod isolated by data and IAM; no long-lived deploy keys; PHI-ready controls (private buckets, no soft-delete retention; no data-residency or BAA work, Tejit r6); cost bounded by config; the owner is emailed when a session fails; adding an LLM or STT provider key = one tfvars line + a seeded value; SP04/05/07 interfaces met exactly; idempotent re-runs.
**Non-goals:** app code, Dockerfile, Firestore index contents (SP04), web config/CSP (SP05), eval-server code (SP07), landing deploy (stays as-is), DNS edits (Tejit), HIPAA BAA/legal, load balancer/Cloud Armor, multi-region, monitoring dashboards, Cloud Scheduler jobs.

**R5 Firestore** (Native, `us-central1`, location is permanent): database `(default)` = prod, `staging` = staging (one project, so the DB is the env boundary). Rules (`root firestore.rules`, deployed to both DBs by CI): `match /session_status/{sid} { allow read: if request.auth != null && request.auth.uid == resource.data.uid; allow write: if false; }` and `match /{document=**} { allow read, write: if false; }`, so the web app reads only its own PHI-free status doc (SP04 R7; because the rule reads `resource.data.uid`, a listen on a missing doc is denied, which is why SP04's `POST /sessions` creates the doc before returning) and every write plus every other collection is server-only (Admin SDK bypasses rules); indexes from `api/firestore.indexes.json` deployed to both DBs by CI via firebase-tools (`firebase.json` lists both databases). **PITR off, no scheduled backups, delete-protection on for prod** so "delete removes everything" holds; TTL policies are not used (auto-expiry deferred in SP04). Prod DB cannot be recovered after an erroneous delete: accepted v1 risk.

**R7 Cloud Tasks** queue `steps-{env}` (`us-central1`): `max_attempts=2` (one retry, per SP04 D3), min backoff 5 s, max backoff 30 s, `max_concurrent_dispatches` = that env's worker capacity (rule: **dispatches ≤ worker concurrency × max-instances**; prod 2 × 3 = 6, staging 2 × 3 = 6; computed in Terraform from the two worker variables, so raising `worker_max_instances` raises it too), `max_dispatches_per_second` 5. The queue therefore never sends the worker more tasks than it can hold, and a task's two attempts are not used up by Cloud Run 429s; a short transcribe poll may wait behind runs when all slots are busy (accepted). The 10-min dispatch deadline is set per task by SP04 (queue config cannot hold it).

## Architecture
```
Browser ─ app.onolys.com ─ Firebase Hosting (site onolys-app: dist/) ─ /v1/** rewrite ─► Cloud Run onolys-api-prod ─► Firestore (default)
   │                                                                                     ├► GCS onolys-audio-prod (signed URLs)
   └─ PUT signed URL (CORS: app origin) ───────────────────────────────────────────────►┘└► Cloud Tasks steps-prod ─OIDC► onolys-worker-prod ─► STT + LLM providers (per config/{env}/*.yaml; keys from llm_secrets/stt_secrets)
   ▲ browser onSnapshot (rules: owner read) ◄── Firestore session_status ◄── worker writes
staging: same shape (site onolys-app-staging, db `staging`, *-staging services) · admin.onolys.com: site onolys-admin ─► Cloud Run onolys-admin-backend-{env} (direct, CORS)
CI: GitHub OIDC ─WIF─► deployer-{env} SA ─► AR push, Cloud Run deploy (GIT_SHA), firebase deploy
Logs (status=failed lines, api 5xx) ─► 2 log-based alerts ─► owner's email channel
```

## Decisions
| # | Decision | Choice | Alternatives considered | Why |
|---|---|---|---|---|
| D1 | Provisioning | Terraform, state in GCS, run locally via ADC | gcloud/bash scripts (simplify-med style); Pulumi | Declarative drift/plan, covers Identity Platform/Hosting/IAM/budget; single binary, no gcloud needed; scripts are not idempotent for IAM |

| D4 | Web/API origin | Hosting site + `/v1/**` rewrite to Cloud Run (same origin) | `api.onolys.com` + CORS; global LB | No CORS/preflight, same stack as landing, free CDN, no LB cost. Rewrite limit 60 s fits (<1 s calls, uploads direct to GCS) |

## Acceptance Criteria
1. `infra/scripts/install-tools.sh` then `bootstrap.sh` then `terraform init/validate/plan` succeed from this machine using ADC with no gcloud and no change to the ADC quota project; a second `plan` after `apply` shows no changes.
2. After apply, per env: bucket private (public access prevention enforced, soft-delete 0, CORS and `uploads/` lifecycle present), queue `steps-{env}` with max_attempts 2, Cloud Run api/worker exist with limits in R8, Firestore DBs `(default)` and `staging` exist with PITR disabled, listed APIs enabled, Identity Platform config active with open sign-up, min password length 8 and no MFA; Firestore rules tests pass on the emulator (owner reads own `session_status`, another user is denied, all client writes denied, every other collection denied; **listener test:** the status doc is created as SP04's `POST /sessions` does, the owner subscribes right after create and the listen succeeds, another user's listen on the same doc is denied, and a listen on a doc that does not exist is denied).
3. IAM check: staging SAs cannot read prod bucket or DB; worker not invokable without the tasks SA OIDC token (401/403 for anonymous); api invokable anonymously.
4. Provider keys: with the default `llm_secrets`, the worker and admin-backend have `ANTHROPIC_API_KEY` as a secret ref and no other provider key; adding a second entry to `llm_secrets` in tfvars produces a plan with exactly one new secret shell, its accessor bindings and env refs, and no change to existing resources; `stt_secrets = {}` creates nothing. The worker has no `STT_*` env var; the deployed image contains `config/{env}/stt_providers.yaml` and `routes.yaml`.
5. Staging deploy via merge to `main` runs end to end with WIF (no JSON key in repo secrets), `GET https://<staging-site>.web.app/v1/healthz` returns 200 through the rewrite, and a signed PUT from the staging origin passes CORS.
6. Prod deploy runs only after environment approval, reuses the staging digest, and prod deployer SA cannot be impersonated from other workflows or forks.
7. Budget exists with thresholds and the notification channel; Cloud Run max-instances and concurrency (worker: 2, prod max 3) and queue `max_concurrent_dispatches` (= concurrency × max-instances; 6 in prod) match R7/R8.
8. `docs/reference/infra.md` lists resource names, env var table, outputs (incl. `VITE_FIRESTORE_DATABASE`), the exact DNS records for `app.` and `admin.` taken from Terraform output, and the runbook (reference id → log query; error-code table; the rollback line).
9. After a staging deploy, api and worker revisions carry `GIT_SHA` equal to the deployed commit; dispatching `deploy-prod` with an earlier sha redeploys api, worker, web and rules from that commit (rollback drill, once).
10. Alerts: a test log line with `status=failed` (written on staging with `staging_alerts=true`, or on prod at launch check) sends one email to the owner's channel; the 5xx metric and its alert policy exist; the runbook query finds that line by its `request_id`.

# PRD: SP04 api + jobs — public API, job orchestration, storage

Repo/branch: Onolys/onolys (local `iaudit`) / `feat/miti-platform` · Depends on: SP01 interfaces (`onolys_core`: `Engine`, `Transcript`, `SttParams/transcribe`, `RunInfo`, `safe_log`, `retry`, uv workspace); SP02/SP03 only via adapters (stubs first) · Owns: `api/**` (package `onolys_api`, workspace member), `api/openapi.json` (committed), `api/Dockerfile`, `api/firestore.indexes.json`, `docs/reference/public-api.md`, `docs/contracts/public/*.schema.json`, `docs/decisions/0020-*`

## TL;DR
One FastAPI codebase, one container image, two Cloud Run roles (`SERVICE_MODE=api|worker`, same pattern as simplify-med). `api` serves `/v1` to the web app (SP05) and API-key clients; every mutation returns immediately (202 + ids). `worker` receives Cloud Tasks, one HTTP task per pipeline **step**, writes progress to `session_status/{sid}` (the only client-readable Firestore doc), and calls engines in-process through an adapter interface (stub engines first). State lives in Firestore, bytes in private GCS. Every query is scoped by `uid`. OpenAPI is generated and committed so SP05 builds against it before the backend exists.

## Problem
SP05 needs a stable contract; SP02/03 engines are not ready; a 3-5 min multi-step job cannot live in one HTTP request; recordings and ratings are PHI-adjacent and need tenant isolation, audit trail, complete deletion and a spend cap.
Verified: eaudit is FastAPI with a contract error body (`error-response.schema.json`, `schema_version` `0.0.1`, closed `details[].code` enum) and `ApiError`/`error_body` helpers [verified: `eaudit/src/eaudit/api/errors.py`]; sync `POST /v1/audit` has a ~100 s deadline, unsuitable for the pipeline. simplify-med proves the api+worker split but uses anonymous auth; we use real accounts, and a client-readable, PHI-free Firestore status document with listeners (r6).

## Goals / Non-Goals
**Goals:** API-first (the web app uses only the API plus a read-only listener on its own `session_status` doc); two auth paths to one `uid`; ≤5 min session target; idempotent steps, one automatic retry per step, stable error codes; per-user daily cap; access audit log; delete removes everything; runs fully locally with emulators/fakes and no GCP.
**Non-goals:** engine logic (SP02/03), UI (SP05), GCP resources/IAM/deploy (SP06; interface below), billing, teams, email, webhooks, transcript editing, trends, admin API (SP07 is separate), changing `POST /v1/audit`.

## Requirements
**R1 Auth.** Dependency `current_user` accepts `Authorization: Bearer <Identity Platform ID token>` (verified with Google public keys, `aud`=project, `iss`, expiry, `email_verified=true` required) **or** `X-API-Key: onolys_<id>_<secret>`. Both resolve to `uid` and `auth_kind`. Token claims are used only for `uid`/email-verified; no PHI is read from or written to auth profiles. API keys: one active per user; `POST/DELETE /v1/api-key`, regenerate = revoke+create; secret shown once; stored as SHA-256 (secret is 32 random bytes, so no slow hash needed) with key id prefix for lookup; constant-time compare; per-key rate limit (default 60 req/min, config; Firestore counter per minute window; `429 rate_limited` + `Retry-After`). Per-uid limit also applies to token auth (same default) to blunt abuse. API key may not manage API keys or delete the account (token only).

Mutation of a session in the wrong state returns `409 invalid_state`. Validation limits (R3) apply on `complete`, not only on client-side checks.
**R3 Upload validation (server-side).** Signed URL pins content-type and size range. `validate` step (worker): GCS object metadata size ≤100 MB; magic-byte sniff vs allowed (mp3, wav, m4a, webm, ogg; audio only, reject video tracks); `ffprobe` (ffmpeg in the image) duration ≤25 min, ≥1 s, ≥1 audio stream; warn `short_recording` if <10 min (stored as session warning, not an error). Failure → `failed` with `unsupported_audio` / `audio_too_long` / `audio_too_large` / `audio_unreadable`, and the object is deleted. Signed URLs target the top-level staging prefix `uploads/{uid}/{sid}/{upload_id}` (audio); `validate` copies a passing object to its final path and deletes the staged one; a GCS lifecycle rule (SP06 R6) deletes `uploads/` objects never completed after 1 day [RESOLVED: top-level `uploads/` staging prefix (reconcile pass)]. 
**R4 Job state machine.** `created → uploaded → validating → transcribing → awaiting_speaker_confirm → awaiting_rating (only if the card is not in yet) → running → report_ready | failed`. Three inputs gate the first run, in any order: (a) transcript ready, (b) speaker confirmed, (c) rating card submitted or "no rating". Transcription starts immediately when the upload completes; the user fills the card while it runs (the card can be submitted before, during or after transcription). When all three are in, the run **starts automatically** (counts against the daily cap, R8); there is no parse or rating-confirm step. `running` has sub-steps `paudit` (N runs, in parallel), `eaudit` (reasons, examples and the notes box as claims), `tips`, `compare`, `assemble`, each a persisted step record; `paudit` and `eaudit` run concurrently, `tips` starts when `paudit` finishes (it needs paudit's instances) and runs alongside `eaudit`, then `compare` + `assemble` (SP03 D5; paudit/eaudit/tips overlap as far as their data dependencies allow, see SP03 Risks). Human gates (`awaiting_*`) are non-terminal and enqueue nothing; the confirm/rating endpoints enqueue the next step when the last input arrives. A re-run starts from `running` on the same transcript/rating (new `run`, new report version). Sessions stuck in an `awaiting_*` gate >7 days: left alone (expiry is a deferred setting). Each state/step/progress change is mirrored to `session_status/{sid}` (R7).

**R5 Execution model** (see Architecture): one Cloud Task per step; step handler loads state, checks `step.status`, does work, writes result, enqueues the next task, in that order; handlers are idempotent (deterministic output paths, set-if-absent writes, task name = `{session}-{run}-{step}-{attempt_epoch}` for dedup within Cloud Tasks' window). **Retry policy: Cloud Tasks queue `max_attempts=2`** (the one automatic retry) with min/max backoff 5-30 s; app logic does **not** add its own loop. Every handler also updates `session_status/{sid}` (state, step, progress, error code). Handler returns 2xx for permanent failures (writes `failed` + error code) so Cloud Tasks does not retry them; returns 5xx only for retryable errors (`upstream_unavailable`, timeouts, 429s) and only when `attempt < 2` (read from `X-CloudTasks-TaskRetryCount`); on the last attempt it records `failed` and returns 2xx. Dispatch deadline per task 10 min; per-step internal deadline 8 min (`RunContext.deadline`). paudit N runs are inside one step by default, but N>3 splits into one task per run (config `run_fanout_threshold`). Step timeouts and Cloud Run request timeout (worker: 15 min) both exceed the internal deadline. Worker auth: Cloud Run requires OIDC from the tasks SA; handler additionally checks the token audience.
**R6 Engine adapters.** `api/adapters.py` defines Protocols that wrap SP01 `Engine`/`transcribe`: `Stt`, `Paudit`, `Eaudit`, `Comparer`, `TipWriter`, `ReportAssembler` (SP03 final shape is theirs; the adapter hides it). adapters map the session's `clinician_speaker` to `speaker_map{subject}` and pass `coded_span{from_s,to_s}` unchanged (SP02/SP03); `ADAPTERS=stub|real` config; **stub** implementations return deterministic typed fixtures (sleep-free, seeded), including failure injection by magic session title for tests. Real adapters are a thin follow-up when SP02/03 land (SP04 acceptance does not require them). `STT` is called with `SttParams` from the preset; `FixtureStt` in tests.

GCS: private buckets, no public access, uniform access; `gs://{audio-bucket}/{uid}/{sid}/audio/…` (the bucket is already per env: SP06 `onolys-audio-{env}`), `…/rating/…`, `…/transcript.json`; signed URLs only, V4. Every Firestore read/write goes through a `Repo` class that requires `uid` and checks `doc.uid == uid` (404 on mismatch, never 403, so ids are not probed); one place, tested with a two-user suite. Firestore security rules (SP06 R5, root `firestore.rules`): `session_status/{sid}` is readable only when `request.auth.uid == resource.data.uid`; **all client writes are denied**; every other collection stays client-denied. The browser reads Firestore only through this one listener and talks to GCS only via signed URLs.
**Delete** (`DELETE /sessions/{id}`): in order, (1) mark `deleting` (blocks reads and new runs; mid-run cancel and the write-after-delete race are not handled in v1 [DEFERRED: edge case, Tejit]), (2) delete all GCS objects under the session prefixes `{uid}/{sid}/` and `uploads/{uid}/{sid}/` (list-and-delete, verified empty), (3) recursive delete of the session doc, its subcollections and `session_status/{sid}`, (4) keep a **content-free** `access_log` tombstone (`resource=session, action=deleted`) for audit; logs hold no content so retention is legal-neutral. Returns 204 only after 2-3 succeed; failures leave `deleting` and a retried cleanup task (idempotent) finishes it. Test enumerates every collection/prefix to prove nothing remains. Backups/PITR: SP06 leaves Firestore PITR **off** in v1 [RESOLVED: SP06 D7 (reconcile pass)].

Over cap: `429 rate_limited` with detail message `daily_cap_reached` text and `resets_at` in `GET /usage`. Concurrent active runs per user ≤2 (config).

## Architecture
```
Browser / API client ──> Cloud Run `api` (FastAPI /v1, returns 202) ──> Firestore ; GCS (signed URLs) ; enqueue Cloud Task
Browser ◄── onSnapshot (owner-only rules) ── Firestore `session_status/{sid}` ◄── worker writes progress
                              │                                  ▲
Cloud Tasks queue `steps` ──OIDC──> Cloud Run `worker` (same image) ── step handler ──> adapters
                                         adapters: Stt(onolys_core) · Paudit · Eaudit · Compare · Tips · Assemble
                                         (stub | real; engines in-process from engines/*)
```
Layout: `api/src/onolys_api/{app.py, auth/, routes/, jobs/{machine,steps,queue}.py, adapters/, repo/{base,firestore,fake}.py, storage/, errors.py, config.py, openapi.py}`, `api/tests/`.
**Long jobs vs timeouts.** User-facing endpoints return in <1 s (enqueue only). Each worker step is bounded (≤8 min internal deadline) inside Cloud Run's 15-min request timeout and Cloud Tasks' 10-min dispatch deadline, so a stalled step fails cleanly instead of hanging. Chaining steps (each step enqueues the next) avoids one 5-min request and lets each step retry independently. Worker `min-instances=0`, CPU always allocated during request (steps are request-bound), concurrency 4, `max-instances` capped (SP06) for spend safety.
**Idempotency.** Client: `Idempotency-Key` on `POST /sessions` and `/runs` (stored with response for 24 h; same key + same body returns original; different body → 409 `conflict`). Server: step records (`pending|running|done|failed`, attempts) + deterministic artifact paths; duplicate task delivery finds `done` and just enqueues-next-if-missing; `running` older than lease (deadline+60 s) is re-claimable via transaction.
**Status contract.** The worker writes `session_status/{sid}` (`{uid, state, step, progress 0-100, error_code, latest_report_version, updated_at, …}`, no text) on every transition; the web app subscribes to it with `onSnapshot` (no polling, no ETag). `GET /sessions/{id}` returns `{status, step, steps[], progress, warnings, error?, latest_report_id}` for API-key clients and as a fallback; everything else (transcript, rating, report) is fetched through the API.

## Acceptance Criteria
1. `uv run --package onolys-api pytest -q` passes with no GCP/network; `api/openapi.json` is committed and a CI check regenerates and diffs it clean.
2. Full stub flow via HTTP: create session → signed upload (fake store) → complete → status reaches `awaiting_speaker_confirm` → confirm; rating card `PUT` (tested both before and after transcription finishes; no parse/confirm step) → run starts automatically → `running` → `report_ready`; second `POST /runs` creates report v2 and keeps v1; dashboard reflects latest.
3. Two-user isolation suite: user B gets 404 on every `{id}` route of user A, API-key and token paths; no collection query lacks a uid filter (test greps repo layer).
4. Auth: invalid/expired/unverified token → 401 `unauthenticated`; revoked key → 401; regenerate invalidates old key; API key hash in store never equals the secret; per-key limit returns 429 with `Retry-After`.
5. Validation: fake files for >100 MB, >25 min, bad type, no audio stream each fail with the specific code and the object is removed; <10 min yields warning only.
6. Retry semantics: injected transient failure on step X succeeds on attempt 2; two failures end `failed` with code and no third attempt; injected permanent error is not retried; duplicate task delivery produces one result.
7. Cap: 21st run of a UTC day returns 429; failure-before-LLM refunds; concurrent requests cannot exceed the cap (transaction test).
8. Delete: after `DELETE`, no GCS object under the prefix and no Firestore doc in any subcollection or `session_status/{sid}` remains (enumerated check); a content-free tombstone exists. (Mid-run delete race: not covered in v1.)
9. Audio and report reads write `access_log`; log-capture test over the full flow finds none of the sentinel transcript/rating/audio strings, tokens or API keys.
10. Every non-2xx body validates against `public-error-response.schema.json`; `request_id` echoed.
11. Async + status doc: every mutation endpoint returns in <1 s with 202 + ids while transcription/engines run in the background; `session_status/{sid}` holds only `{uid, state, step, progress, error_code, latest_report_version, updated_at, flags}` (schema test: no transcript/rating/report text); rating card `PUT` above 1,000 chars/item or 3,000 notes → 422 `rating_invalid`; no file-upload or parse endpoints in `openapi.json`.
12. `SERVICE_MODE=combined` local run works with `scripts/dev.sh`-style one command and fakes; worker rejects calls without valid OIDC outside `ENV=local|test`.

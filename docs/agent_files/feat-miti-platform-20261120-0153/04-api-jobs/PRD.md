Repo/branch: Onolys/onolys (local `iaudit`) / `feat/miti-platform` · Depends on: SP01 interfaces + presets (`onolys_core`: `SttAdapter`/`SttParams`/`AudioRef`, `Transcript`, `RunInfo`, `safe_log`, `retry`, the routes/presets file, `config/{env}/stt_providers.yaml`, uv workspace); SP02 `rating.schema.json`; SP03 `validate_rating` + `run_evaluation` (until SP03 lands, SP04's `validate_rating` is jsonschema-only against the SP02 schema). ## TL;DR
One FastAPI codebase, one container image, two Cloud Run roles (`SERVICE_MODE=api|worker`, same pattern as simplify-med). `api` serves `/v1` to the web app (SP05) and API-key clients; every mutation returns immediately (202 + ids). `worker` receives Cloud Tasks (`validate`, `transcribe` + delayed polls, and **one task for the whole evaluation run**), writes progress to `session_status/{sid}` (the only client-readable Firestore doc), and calls engines in-process through two adapters, `Stt` and `Evaluation` (fake adapters first; real ones in SP09). State lives in Firestore, bytes in private GCS. Every query is scoped by `uid`. OpenAPI is generated and committed so SP05 builds against it before the backend exists.

## Problem
SP05 needs a stable contract; SP02/03 engines are not ready; a 3-5 min multi-step job cannot live in one HTTP request; recordings and ratings are PHI-adjacent and need tenant isolation, complete deletion and a spend cap.
Verified: eaudit is FastAPI with a contract error body (`error-response.schema.json`, `schema_version` `0.0.1`, closed `details[].code` enum) and `ApiError`/`error_body` helpers [verified: `eaudit/src/eaudit/api/errors.py`]; sync `POST /v1/audit` has a ~100 s deadline, unsuitable for the pipeline. simplify-med proves the api+worker split but uses anonymous auth; we use real accounts, and a client-readable, PHI-free Firestore status document with listeners (r6).

## Goals / Non-Goals
**Goals:** API-first (the web app uses only the API plus a read-only listener on its own `session_status` doc); two auth paths to one `uid`; **time target: ≤5 min from run start (the last of transcript, speaker confirm and final card is in) to `report_ready`, at N=1** (transcription is not counted: it runs while the user fills the card and its p95 is recorded by the SP01 gate; SP09 measures both on staging); idempotent tasks, one automatic retry per task, stable error codes; per-user daily cap; delete removes everything; STT/LLM provider and model never named in SP04 code (session `stt` + preset names only); runs fully locally with emulators/fakes and no GCP.
**Non-goals:** engine logic (SP02/03), UI (SP05), GCP resources/IAM/deploy (SP06; interface below), billing, teams, email, webhooks, transcript editing, trends, admin API (SP07 is separate), changing `POST /v1/audit`.

## Requirements
**R1 Auth.** Dependency `current_user` accepts `Authorization: Bearer <Identity Platform ID token>` (verified with Google public keys, `aud`=project, `iss`, expiry, `email_verified=true` required) **or** `X-API-Key: onolys_<id>_<secret>`. Both resolve to `uid` and `auth_kind`. Token claims are used only for `uid`/email-verified; no PHI is read from or written to auth profiles. API keys: one active per user; `POST/DELETE /v1/api-key`, regenerate = revoke+create; secret shown once; stored as SHA-256 (secret is 32 random bytes, so no slow hash needed) with key id prefix for lookup; constant-time compare. Per-request rate-limit counters (per key / per uid, per minute) are **After launch**: v1 relies on Cloud Run max-instances (SP06 R8) and the daily run cap (R8); the code `rate_limited` stays reserved for those per-minute limits. API key may not manage API keys or delete the account (token only).
**R2 Endpoints** (all under `/v1`, JSON, uid-scoped; contract = OpenAPI + `docs/contracts/public/`). **Every mutation returns immediately** (no endpoint waits for transcription or engines): calls that trigger work return `202` with ids (session/run/step); the worker does the rest and writes `session_status/{sid}` (R7), which the web app watches with a Firestore listener instead of polling. Mutation of a session in the wrong state returns `409 invalid_state`. Validation limits (R3) apply on `complete`, not only on client-side checks.
**R3 Upload validation (server-side).** Signed URL pins the canonical content-type and size range (cap 300 MB: an ordinary 16-bit stereo WAV is about 10 MB per minute). `validate` step (worker): GCS object metadata size ≤300 MB; magic-byte sniff vs allowed (mp3, wav, m4a, webm, ogg; audio only, reject video tracks); `ffprobe` (ffmpeg in the image) duration ≤25 min, ≥1 s, ≥1 audio stream; warn `short_recording` if <10 min (stored as session warning, not an error). Failure → `failed` with `unsupported_audio` / `audio_too_long` / `audio_too_large` / `audio_unreadable`, and the object is deleted. Signed URLs target the top-level staging prefix `uploads/{uid}/{sid}/{upload_id}` (audio); `validate` moves a passing object to `{uid}/{sid}/audio/original.{ext}`, **transcodes it with ffmpeg to FLAC 16 kHz mono at `{uid}/{sid}/audio/canonical.flac`** (transcode failure → `audio_unreadable`) and deletes the staged one; STT always receives the canonical file as `AudioRef{uri, local_path_fn, mime, duration_ms}` (SP01), never a browser format; a GCS lifecycle rule (SP06 R6) deletes `uploads/` objects never completed after 1 day [RESOLVED: top-level `uploads/` staging prefix (reconcile pass)]. 
**R4 Job state machine.** `state` enum: `created | uploading | validating | transcribing | awaiting_input | running | report_ready | failed | deleting`. Path: `created → uploading` (`POST …/audio`) `→ validating` (`…/audio/complete`) `→ transcribing → awaiting_input → running → report_ready | failed`. There is one human-wait state, `awaiting_input`; which input is missing is told by four flags kept on `sessions/{sid}` and mirrored to `session_status/{sid}`: `transcript_ready`, `speaker_confirmed`, `rating_submitted` (a final revision or "no rating" exists; drafts do not count) and `has_rating` (that revision carries scores/counts/notes). The UI derives "confirm speaker" / "your rating" from the flags. Transcription starts immediately when the upload completes; the card can be saved before, during or after it; there is no parse or rating-confirm step.
*First run (auto-start).* Three inputs gate it: transcript ready, speaker confirmed, rating submitted (final card or "no rating"). They can arrive in any order and at the same moment (from `PUT rating`, `speakers/confirm` or the transcribe worker), so each of the three calls `maybe_start_first_run(sid)`: **one Firestore transaction** that reads the session and, only if all three flags are true and `first_run_id` is absent, checks the cap (R8), creates the run (snapshot of `rating_id`, `n_runs`, `preset`, `stt`, `code_version`), sets `first_run_id` and `state=running`. The `run` task is enqueued after commit under a name derived from `run_id` (a duplicate enqueue is a no-op), so exactly one first run starts. If the daily cap or the concurrent-run limit is hit, nothing starts: state stays `awaiting_input` with `error_code=daily_cap_reached`, and the user starts it later with `POST /runs` (which clears the code).
*Transcribe.* The `transcribe` step calls `SttAdapter.start(audio, params)` once, stores the returned handle as `stt_operation` on its step record and enqueues a delayed poll task (about every 15 s; `poll(handle) -> Transcript | None`) until done, for at most about 20 min in total. A retry or redelivery finds `stt_operation` and resumes polling; it never re-submits. Failures → `failed` (user action "Upload a different file"): `no_speech` (0 turns or <50 words), `speakers_not_separated` (<2 speakers, or the smaller speaker has <10% of the words), `transcription_failed` (provider error, or no result within the limit). `speakers_min`/`speakers_max` default to 2/2 (SP01 R4: a mock interview has two people), so the default provider entry never returns more than 2 speakers; the more-than-2-speakers picker (the session proceeds and the gate lists all of them, R2) applies only when a `stt_providers.yaml` entry raises `speakers_max`. Re-running STT on an existing session (other provider/model/language) is [DEFERRED]: upload again.
*Run.* `running` is **one Cloud Task** that calls SP03 `run_evaluation(..., progress_cb(stage, status))` in-process through the `Evaluation` adapter (R6); asyncio inside it does the parallelism (`paudit` ‖ `eaudit`, `tips` after `paudit`, then `compare`, `assemble`). Those five stage names are progress labels only: not separate tasks, not step records. `progress_cb` is called with stage ∈ `paudit | eaudit | tips | compare | assemble` and status ∈ `started | done | failed` (SP03 R1); it writes `session_status.step` (the stage last `started`) and adds the stage's weight to `progress` on `done` or `failed`, from the fixed table below. A retry re-runs the whole run. Partial failure: `paudit` failure (or all N scoring runs failing) = run and session `failed`; `eaudit` or `tips` failure = the report is still assembled, with `reasons_audit.status = failed|partial` + report warning `reasons_audit_failed|reasons_audit_partial`, or `tips = []` + warning `tips_failed`, and the state is `report_ready`. A re-run (`POST /runs`) goes `report_ready|failed → running` on the same transcript with the latest final rating revision and speaker choice (new `run`, new report version). `awaiting_input` enqueues nothing and is left alone however long it lasts (expiry is a deferred setting). Every state/step/progress/flag change is mirrored to `session_status/{sid}` (R7).
| | `created` | `uploading` | `validating` | `transcribing` | `awaiting_input` | `running` starts | `paudit` done | `eaudit` done | `tips` done | `compare` done | `assemble` done |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `progress` | 0 | 5 | 10 | 20 | 40 | 45 | +25 | +15 | +8 | +4 | +3 (= 100, `report_ready`) |
Stage weights add up in whatever order stages finish (a stage that fails or is skipped still adds its weight), so `progress` never goes backwards within a run; `failed` keeps the last value; a re-run restarts at 45.

**R5 Execution model** (see Architecture): four task kinds on one queue: `validate`, `transcribe` (start), `transcribe-poll` (delayed, re-enqueued until the STT operation is done) and `run` (the whole evaluation), plus the delete cleanup task. A handler loads state, checks the step/run `status`, does work, writes the result, enqueues what follows, in that order; handlers are idempotent (deterministic output paths, set-if-absent writes, task names `{sid}-validate`, `{sid}-transcribe`, `{sid}-poll-{n}`, `{run_id}-run` for dedup within Cloud Tasks' window). **Retry policy: Cloud Tasks queue `max_attempts=2`** (the one automatic retry) with min/max backoff 5-30 s; app logic does **not** add its own loop. Every handler also updates `session_status/{sid}` (state, step, progress, error code). Handler returns 2xx for permanent failures (writes `failed` + error code) so Cloud Tasks does not retry them; returns 5xx only for retryable errors (`upstream_unavailable`, timeouts, 429s) and only when `attempt < 2` (read from `X-CloudTasks-TaskRetryCount`); on the last attempt it records `failed` and returns 2xx. Dispatch deadline per task 10 min; internal deadline 8 min (`RunContext.deadline`) for `validate` and `run`; `transcribe` and each poll return in seconds (a poll that finds no result re-enqueues the next poll and returns 2xx; it is not a retry). The N scoring runs are asyncio tasks inside the one `run` task; there is no fan-out into separate tasks. Task timeouts and Cloud Run request timeout (worker: 15 min) both exceed the internal deadline. Worker auth: Cloud Run requires OIDC from the tasks SA; handler additionally checks the token audience.
**R6 Engine adapters.** `api/adapters.py` defines exactly two Protocols. `Stt` wraps the provider-neutral SP01 interface: `SttAdapter.start(audio: AudioRef, params: SttParams) -> handle` and `poll(handle) -> Transcript | None`, with `SttParams{provider, model, language, diarization, speakers_min, speakers_max, options}` built from the session's stored `stt` (R2) and `AudioRef` pointing at `canonical.flac` (R3); SP04 never reads provider-specific fields. `Evaluation` wraps SP03 `run_evaluation` (SP03 R1): in = `ctx` (core `RunContext`: LLM client for the run's preset, deadline, `request_id`), the pack, transcript, `speaker_map{subject}` from the session's `clinician_speaker` (every other speaker = client), `params{change_goal, coded_span{from_s,to_s} unchanged, language, n_runs, preset, code_version}`, the snapshotted rating revision or none, and `progress_cb(stage, status)`; the report header's `stt` comes from `transcript.stt_run`; out = `EvaluationOutput{report, artifacts{paudit, eaudit, tips}}` (report JSON incl. its `run_info`, plus the run artifacts `PauditResult`, eaudit response, tips). There are no per-stage adapters. `ADAPTERS=stub|real` config; the **fake** (`stub`) implementations return deterministic schema-valid fixtures (sleep-free, seeded), call `progress_cb` for every stage, and support failure injection by magic session title (paudit failed; eaudit failed and tips failed as partial reports; the three transcribe codes). SP04 acceptance uses only the fakes. The real `Stt`/`Evaluation` adapters, the engine-error → public-code mapping and the staging end-to-end run are owned by SP09 (`09-integration`). `FixtureStt` in tests.

GCS: private buckets, no public access, uniform access; `gs://{audio-bucket}/{uid}/{sid}/audio/{original.{ext},canonical.flac}` (the bucket is already per env: SP06 `onolys-audio-{env}`), `…/transcript.json` and `…/reports/{report_id}.json` (each only when >500 KB), run artifacts `{uid}/{sid}/runs/{run_id}/{paudit,eaudit,tips}.json` (written by the `run` task for debugging and evaluation; never served to clients); signed URLs only, V4. Every Firestore read/write goes through a `Repo` class that requires `uid` and checks `doc.uid == uid` (404 on mismatch, never 403, so ids are not probed); one place, tested with a two-user suite. **Delete** (`DELETE /sessions/{id}`): in order, (1) mark `deleting` (blocks reads and new runs; mid-run cancel and the write-after-delete race are not handled in v1 [DEFERRED: edge case, Tejit]), (2) delete all GCS objects under the session prefixes `{uid}/{sid}/` and `uploads/{uid}/{sid}/` (list-and-delete, verified empty), (3) recursive delete of the session doc, its subcollections and `session_status/{sid}`, (4) write one **content-free** structured log line (`action=session_deleted`, `session_id`, `uid_hash`, `request_id`); no tombstone document is kept. **R8 Cap and limits.** Daily run cap per uid (config `DAILY_RUN_CAP=20`, UTC day, per-user override field on `users/{uid}`): checked and incremented atomically in a Firestore transaction when a run is created (auto-start, R4, or `POST /runs`); refunded if the run fails before any LLM call. Over cap on `POST /runs`: HTTP 429 with `details[].code=daily_cap_reached` (`resets_at` in `GET /usage`); at auto-start nothing is returned to anyone, so the session stays `awaiting_input` with `error_code=daily_cap_reached` (R4). `rate_limited` is only for per-minute limits (R1, After launch). Concurrent active runs per user ≤2 (config), handled the same way.
**R9 Error schema.** Reuse `error-response.schema.json` body shape verbatim. New codes are needed (`unauthenticated`, `forbidden`, `invalid_state`, `unsupported_audio`, `audio_too_long`, `audio_too_large`, `audio_unreadable`, `no_speech`, `speakers_not_separated`, `transcription_failed`, `rating_invalid`, `daily_cap_reached`, `conflict`). The enum is closed and owned by the frontend contract, so SP04 **extends the enum in a new `public-error-response.schema.json`** (superset, same `schema_version "0.0.1"`) and leaves the eaudit schema untouched (the sync audit API keeps its own). `ApiError` and `error_body` are imported/moved via core in a follow-up; initially re-implemented in `onolys_api.errors` (tiny). Messages carry fixed text only, never instance values; status equals HTTP status; `request_id` echoed.
**R10 Logging/privacy.** `onolys_core.safe_log` allowlist only; register api fields (`uid_hash` (HMAC), `session_id`, `run_id`, `step`, `status`, `attempt`, `duration_ms`, `auth_kind`, `error_code`, `exc_class`, `request_id`, `code_version`). Every failed step or run writes exactly one log line with `status=failed` carrying `session_id, run_id, step, error_code, exc_class, request_id` (the `request_id` of the API call that started the work travels in the task payload; `exc_class` is the exception class name only, never its message); SP06's failure alert and runbook query match on it. Never log transcript, rating, report text, audio URIs with signatures, tokens or keys. Request logging middleware logs method, route template (not path with ids of other tenants beyond session id), status, latency. Test: capture logs across the full stub pipeline; assert no sentinel strings from audio/transcript/rating fixtures.
**R11 OpenAPI + client.** `api/openapi.json` generated by `python -m onolys_api.openapi` and committed; CI fails if stale. The API serves it at `/v1/openapi.json` and a public Redoc page at `/v1/docs` with the curl quickstart (R2); the web "API docs" link points there. SP05 generates a TypeScript client from it. Stable `operationId`s, response models for every code, `Idempotency-Key` documented on `POST /sessions`. CORS: allowed origins = `app.onolys.com` (+ `staging` host, localhost in dev); Authorization/X-API-Key/Idempotency-Key headers.
**R12 Local dev & tests.** `SERVICE_MODE=combined` runs api+worker in one process with an in-memory task queue that calls handlers directly (no Cloud Tasks). Firestore via emulator (`firebase emulators`, port in env; also used for the rules tests) **or** the `FakeRepo` in-memory implementation behind the same `Repo` protocol (it records `session_status` writes); GCS via `FakeBlobStore` (local dir, fake signed URLs served by the app) or emulator; auth via `AUTH_MODE=fake` accepting `Bearer test:<uid>` (rejected unless `ENV=local|test`). Tests: pytest, httpx ASGI client, fake engines, `FixtureStt`, ffprobe stubbed with tiny generated wav fixtures (one real ffprobe + ffmpeg transcode test marked `integration`). No test needs network or GCP. Real engines locally (once SP09 lands): `ADAPTERS=real` with a local `stt_providers.yaml` whose default entry is `provider: fixture` (there is no STT env var) + `ANTHROPIC_API_KEY` runs the real evaluation on a fixture transcript with no GCP; `AudioRef.local_path_fn` hands the STT adapter a local file, so real STT also works without GCS.

## Architecture
```
Browser / API client ──> Cloud Run `api` (FastAPI /v1, returns 202) ──> Firestore ; GCS (signed URLs) ; enqueue Cloud Task
Browser ◄── onSnapshot (owner-only rules) ── Firestore `session_status/{sid}` ◄── worker writes progress
                              │                                  ▲
Cloud Tasks queue `steps` ──OIDC──> Cloud Run `worker` (same image) ── task handler ──> adapters
   tasks: validate · transcribe · transcribe-poll (delayed, repeats) · run (whole evaluation)
                                         adapters: Stt (SP01 SttAdapter start/poll) · Evaluation (SP03 run_evaluation + progress_cb)
                                         (stub | real; engines in-process from engines/*; real wiring = SP09)
```
Layout: `api/src/onolys_api/{app.py, auth/, routes/, jobs/{machine,steps,queue}.py, adapters/, repo/{base,firestore,fake}.py, storage/, errors.py, config.py, openapi.py}`, `api/tests/`.
**Long jobs vs timeouts.** User-facing endpoints return in <1 s (enqueue only). Each worker task is bounded (≤8 min internal deadline) inside Cloud Run's 15-min request timeout and Cloud Tasks' 10-min dispatch deadline, so a stalled task fails cleanly instead of hanging. Transcription never holds a request open: the provider's long-running operation is polled by short delayed tasks. The evaluation is one request (target ≤5 min from run start to report) because its stages share in-memory data and asyncio already runs them in parallel; splitting it into tasks bought only bookkeeping. Worker `min-instances=0`, CPU always allocated during request (tasks are request-bound), **concurrency 2** (a `run` holds many LLM calls and a `validate` holds an ffmpeg transcode), `max-instances` capped (SP06: prod 3 until measured) for spend and LLM rate-limit safety; the LLM client backs off on 429 (SP01).
**Idempotency.** Client: `Idempotency-Key` on `POST /sessions` only (stored with response for 24 h; same key + same body returns original; different body → 409 `conflict`); `POST /runs` has no key store in v1, the concurrent-run limit and the daily cap bound a double click. Server: step records for `validate`/`transcribe` and the run record (`pending|running|done|failed`, attempts) + deterministic artifact paths; the first-run transaction (`first_run_id`, R4); duplicate task delivery finds `done` and just enqueues-next-if-missing; `running` older than lease (deadline+60 s) is re-claimable via transaction.
**Status contract.** The worker writes `session_status/{sid}` (`{uid, state, step, progress 0-100, error_code, latest_report_version, updated_at, transcript_ready, speaker_confirmed, rating_submitted, has_rating}`, no text) on every transition, starting from the doc `POST /sessions` creates; the web app subscribes to it with `onSnapshot` (no polling, no ETag). `GET /sessions/{id}` returns `{status, step, progress, flags{…}, warnings, error?, latest_report_version}` for API-key clients and as a fallback; everything else (transcript, rating, report) is fetched through the API.

## Decisions
| # | Decision | Choice | Alternatives considered | Why |
|---|---|---|---|---|
| D1 | Framework | FastAPI (+pydantic) | Flask, Litestar | eaudit and simplify-med use it; free OpenAPI; shared error helpers |
| D2 | Task granularity | `validate`, `transcribe` (+ delayed polls) and ONE `run` task that calls `run_evaluation` in-process; stages are progress labels (r7 audit (2026-11-20)) | One task per stage, chained, with per-stage adapters and a fan-out threshold; Workflows/Pub/Sub | The stages share in-memory data and asyncio already parallelises them; per-stage tasks added step records, six adapters and fan-out config for no user benefit. A retry re-runs the whole run |
| D3 | Retry | Cloud Tasks `max_attempts=2` only; permanent errors return 2xx | App-level retry loop; Cloud Tasks unlimited | One retry rule, no 2x2 multiplication; error semantics explicit |
| D4 | Status delivery | PHI-free `session_status/{sid}` Firestore doc + client `onSnapshot`; `GET` kept for API-key clients | Polling with ETag; SSE | Faster feel, less load (Tejit r6); the doc holds no text so owner-only client reads are safe |
| D5 | Upload | Single signed PUT URL to GCS (≤300 MB, server-chosen canonical `Content-Type` returned as `required_headers`) + `complete` call + server `ffprobe` + transcode to `canonical.flac` (r7 audit (2026-11-20)) | Proxy upload through Cloud Run; a smaller cap; pass the browser's format to STT | Cloud Run 32 MB request cap; ffprobe in image gives real duration; the earlier, smaller cap rejected ordinary WAV at ~9 min; browsers send several MIME aliases for one format; one audio format in front of STT keeps the provider swappable |
| D6 | Process model | One image, `SERVICE_MODE` api/worker/combined | Two images | Same code, one build; combined mode = local dev |
| D7 | Tenant isolation | `Repo` requires uid, 404 on mismatch; rules deny clients except owner read of `session_status` | Per-collection ad hoc checks; broader Firestore client rules | Single audited choke point; PHI never read from browser |
| D8 | User-chosen models | Allowlisted `preset` only | Free-form stt/llm overrides | Cost control; full overrides stay admin/eval |
| D9 | Key hashing | SHA-256 of 256-bit secret, id prefix lookup | bcrypt/argon2 | High-entropy secret; fast auth on every call |
| D10 | Error enum | New superset schema `public-error-response` | Edit eaudit schema; reuse as is | Existing enum is closed/frontend-owned; avoids touching 0.0.1 sync API |
| D11 | Transcript storage | Firestore doc ≤500 KB else GCS pointer | Always GCS; always Firestore | 1 MiB doc limit vs 25-min transcripts (~40 KB typical) |
| D12 | Re-run | New `run` + new report version on the same transcript; it takes the latest final rating revision and speaker choice; a re-run `preset` changes LLM routes only | Overwrite; re-run STT | Brief decision; old versions kept; dashboard uses latest; re-running STT is Deferred (r7 audit (2026-11-20)) |
| D13 | Session state | One wait state `awaiting_input` + flags `transcript_ready, speaker_confirmed, rating_submitted, has_rating`; first run started inside one transaction that sets `first_run_id` (r7 audit (2026-11-20)) | Two separate wait states (speaker, rating); start from whichever endpoint saw the last input | Inputs arrive in any order and at once; two wait states could not express "both missing" and raced into two runs or none |
| D14 | Cap at auto-start | Stay `awaiting_input` + `error_code=daily_cap_reached`; user starts with `POST /runs`; API error = 429 `daily_cap_reached` (r7 audit (2026-11-20)) | Fail the session; reuse `rate_limited` | Nothing is lost when the cap resets; one code per cause |
| D15 | Rating writes | `PUT rating` with `final`; drafts autosaved and never gate; each final PUT = new revision; run snapshots `rating_id`; allowed in every state but `deleting`; Firestore only (r7 audit (2026-11-20)) | Replace until a run starts; raw objects under a GCS `rating/` prefix | Closing the tab loses nothing; a rating can be added or changed after a report and applied by "Run again" |
| D16 | Transcribe | Store `stt_operation`, poll with delayed tasks ≤~20 min, resume on retry; codes `no_speech`, `speakers_not_separated`, `transcription_failed`; `SttAdapter.start/poll` with `AudioRef`/`SttParams` from the session's stored `stt` (r7 audit (2026-11-20)) | Block one request until STT returns; re-submit on retry | A retry must not pay for STT twice; bad diarization must stop before LLM spend; provider-neutral call |
| D17 | Partial failure | paudit failed = run `failed`; eaudit/tips failed = report with `reasons_audit.status=failed\|partial` (`reasons_audit_failed\|reasons_audit_partial`) or `tips=[]` (`tips_failed`), `report_ready` (r7 audit (2026-11-20)) | Any stage failure fails the run | The ratings comparison is the product; the rest is recoverable by "Run again" |
| D18 | API surface | Added `GET /sessions`, `GET /sessions/{id}/reports/{version}`, `/v1/openapi.json` + `/v1/docs`, `{run_id}`/`{report_id}` names, report >500 KB to GCS, run artifacts in GCS, `stt`/`preset`/`code_version` on run + report header, `session_status` created by `POST /sessions` (r7 audit (2026-11-20)) | Report addressed only by internal id; dashboard built from reports | Failed and in-flight sessions must be listable; a report address a person can read; a run must say what produced it |
| D19 | Cuts to After launch | `GET /presets`, `GET /dashboard` aggregates, the access-log collection + delete tombstone doc, per-request rate-limit counters, `Idempotency-Key` store on `POST /runs` (owner-approved, r7 audit (2026-11-20)) | Keep in v1 | Not needed for the first early-access users; Cloud Run max-instances + daily cap bound abuse; `n_runs`/`preset` params stay in the API |
| D20 | Real engines | Fake `Stt`/`Evaluation` adapters here; real adapters, error mapping and staging end-to-end in SP09 (r7 audit (2026-11-20)) | "Thin follow-up" with no owner | Integration needs an owner and its own acceptance |

## Acceptance Criteria
1. `uv run --package onolys-api pytest -q` passes with no GCP/network; `api/openapi.json` is committed and a CI check regenerates and diffs it clean.
2. Full stub flow via HTTP: create session → signed upload (fake store) → complete → state reaches `awaiting_input` with `transcript_ready=true` → confirm speaker; rating card `PUT final=true` (tested both before and after transcription finishes; no parse/confirm step) → run starts automatically → `running` → `report_ready`; second `POST /runs` creates report v2 and keeps v1 (`GET /sessions/{id}/reports/1` and `/2` both resolve); `GET /sessions` lists the session with `latest_report_version=2`, and also lists a failed and an in-flight session.
3. Two-user isolation suite: user B gets 404 on every `{id}` route of user A, API-key and token paths; no collection query lacks a uid filter (test greps repo layer).
4. Auth: invalid/expired/unverified token → 401 `unauthenticated`; revoked key → 401; regenerate invalidates old key; API key hash in store never equals the secret.
5. Validation: fake files for >300 MB, >25 min, bad type, no audio stream each fail with the specific code and the object is removed; <10 min yields warning only. `POST …/audio` with `audio/x-m4a`, `audio/mp4`, `audio/mpeg` and an empty type + extension each return `required_headers` with the canonical type; a passing upload leaves `audio/canonical.flac` (FLAC, 16 kHz, mono; integration test with real ffmpeg) and the `Stt` fake receives an `AudioRef` to it.
6. Retry semantics: injected transient failure on a task succeeds on attempt 2; two failures end `failed` with code and no third attempt; injected permanent error is not retried; duplicate task delivery produces one result; a retried `run` task re-runs the whole evaluation and yields one report. Transcribe: `start` is called exactly once across a retry and a redelivery (the stored `stt_operation` is resumed), polls stop at the time limit with `transcription_failed`, and fixtures for 0 turns / <50 words / one speaker / a 5% second speaker end `failed` with `no_speech` / `speakers_not_separated`; a 3-speaker fixture reaches the gate listing 3 speakers.
7. Cap: 21st run of a UTC day returns 429 with `details[].code=daily_cap_reached`; failure-before-LLM refunds; concurrent requests cannot exceed the cap (transaction test). Cap hit at auto-start: session stays `awaiting_input` with `error_code=daily_cap_reached`, and a later `POST /runs` starts the run.
8. Delete: after `DELETE`, no GCS object under the prefix (audio, transcript, report and run-artifact objects included) and no Firestore doc in any subcollection or `session_status/{sid}` remains (enumerated check); one content-free `session_deleted` log line exists. (Mid-run delete race: not covered in v1.)
9. Log-capture test over the full flow finds none of the sentinel transcript/rating/audio strings, tokens or API keys; an injected failure produces exactly one `status=failed` line with `session_id, run_id, step, error_code, exc_class, request_id`.
10. Every non-2xx body validates against `public-error-response.schema.json`; `request_id` echoed.
11. Async + status doc: every mutation endpoint returns in <1 s with 202 + ids while transcription/engines run in the background; `session_status/{sid}` holds only `{uid, state, step, progress, error_code, latest_report_version, updated_at, flags}` (schema test: no transcript/rating/report text), exists as soon as `POST /sessions` returns, and its `progress` follows the R4 table and never decreases within a run; rating card `PUT` above 1,000 chars/item or 3,000 notes → 422 `rating_invalid`; no file-upload or parse endpoints in `openapi.json`.
12. `SERVICE_MODE=combined` local run works with `scripts/dev.sh`-style one command and fakes; worker rejects calls without valid OIDC outside `ENV=local|test`.
13. First-run race: `PUT rating final=true`, `speakers/confirm` and the transcribe completion fired concurrently (all orders, repeated) create exactly one run and one `run` task; `first_run_id` is set once.
14. Rating: a draft (`final=false`) is stored and returned by `GET` but never starts a run and never changes `rating_submitted`; each `final=true` PUT creates a new revision; a run records the `rating_id` it used; a final PUT in `report_ready` followed by `POST /runs` yields a report on the new revision (incl. no-rating → rated); PUT is rejected only in `deleting`; no object is written under any GCS rating path.
15. Partial failure (fake injection): paudit failed → run and session `failed`; eaudit failed → `report_ready` with `reasons_audit.status=failed` and warning `reasons_audit_failed`; tips failed → `report_ready` with `tips=[]` and warning `tips_failed`.
16. Run record and report header carry `stt`, `preset` and `code_version` (= `GIT_SHA`); run artifacts exist at `{uid}/{sid}/runs/{run_id}/{paudit,eaudit,tips}.json`; a report fixture over 500 KB is stored in GCS and served unchanged by `GET /sessions/{id}/reports/{version}`; a re-run with another `preset` reuses the transcript (the `Stt` fake is not called again).
17. `/v1/openapi.json` and `/v1/docs` answer 200 without auth; the docs page loads no script from another host; the quickstart's curl sequence is executed by a test against `SERVICE_MODE=combined`. `openapi.json` has no `/presets`, `/dashboard` or top-level `/reports/…` paths, and every path id is named `{id}` (session), `{run_id}`, `{report_id}` or `{version}`.
18. `speakers/confirm` in `report_ready` changes `clinician_speaker` for the next run only (the existing report is unchanged).
